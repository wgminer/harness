Harness Coding Agent Audit

An audit of OpenCode, Codex, Pi and Cline from their current source, a map of the Harness coding agent as it stands, and a proposed redesign: a small, Pi-style agent loop with undo and mid-turn steering built in.

Source snapshots read on 2026-10-09: sst/opencode@055d95b, openai/codex@7efd184, badlogic/pi-mono@42a3497, cline/cline@d20b337. Harness at main@ed9526f plus uncommitted WIP. File paths below are relative to each repo.

Recommendation

Build Harness's coding agent the way Pi builds its agent: four tools, a short prompt, and a loop that keeps going until the model stops calling tools. That way most capability gains come from switching to a better model, not from harness features. Spend the complexity budget on three things the user handles directly: steering, undo, and approvals you rarely see.

The proposal in nine decisions

  1. Fix the loop before adding features. Harness doesn't send earlier turns' tool calls back to the model, and it stops after 10 tool rounds without saying so. Both have to be fixed before steering or undo can be trusted.
  2. Steer by default, queue on request. While a turn runs, Enter sends a steer and ⌥ Enter queues a follow-up. Pi, Codex and the Copilot SDK all work this way. Harness applies the steer in its own loop after the in-flight tool call finishes, so it works with any model and doesn't depend on server-side steering support.
  3. Undo per turn, using a separate snapshot repo. A hidden git directory in app data, snapshotted at the start of each turn and after each mutating tool. Restore can roll back files, the conversation, or both. The user's own .git is never touched.
  4. Four tools: read, edit (an edits[] array), write, bash. The list, search, delete and git tools fold into bash. Once undo exists, edits run without asking by default. Shell commands go through a permission rules contract that supports "always allow npm test *" and "deny with a note to the agent".
  5. Show the work as it happens. Each turn becomes a timeline of text and tool calls in the order they happened. Each call shows live status, its command or path, its output and result, and how long it took. Today one card sits above the reply, failed calls get a checkmark, and no output is shown. See Tool display and UX.
  6. Make web search strong. Upgrade web_search (domain and recency filters, deeper results, parallel calls, visible sources) and add web_fetch to read a full page. These are the only two tools added beyond Pi's four. See Web search.
  7. Attach by reference, not by copy. @ mentions with a fuzzy file picker, image attachments, and folder drops that add workspace folders. The workspace becomes a root plus added folders, each read-only or read-write, and reads outside it ask once. See Attachments and folder access.
  8. The phone views and queues. iOS has no coding agent. It renders coding turns from synced display items, using a shared toolDisplay.json contract, and can queue a "run on desktop" job that the desktop picks up when you're back. See Desktop and iOS.
  9. Defer Plan mode, subagents, sandboxing and an HTTP server. Add a loop guard and compaction once the core works. Shape the IPC events after Codex's Thread/Turn/Item model, so a headless client could be added later without redesigning them.

Steering, undo and web search are the three priorities. The timeline display ships first, because steering and undo both need it to show where things happened.

This reorders your provisional ranking. Steering moves to the top as you asked. Undo stays second. The history-replay fix is a new prerequisite. Pattern-based "always allow" becomes part of a broader permissions slice. Plan mode and the explore subagent drop out of the first pass, because with steering and undo in place they solve problems you will mostly no longer have.

Corrections to the first pass

Six of the first-pass findings differ from what the current source does.

  • OpenCode does not deny .env reads; it asks. The defaults are read: {"*": "allow", "*.env": "ask", "*.env.*": "ask", "*.env.example": "allow"}. The broader default is "*": "allow": out of the box, Build only asks for doom_loop and paths outside the project. packages/opencode/src/agent/agent.ts:116-135
  • OpenCode's Explore is read-only only by convention, and there is no "Scout" agent. Explore allows bash, so nothing stops it writing through the shell. The built-in agents are build, plan, general and explore, plus hidden compaction, title and summary agents. agent/agent.ts:196-262
  • OpenCode gives GPT models apply_patch instead of edit/write. Any model ID containing gpt- (except oss and gpt-4) gets the patch tool. That matters for Harness, which defaults to gpt-5.4. tool/registry.ts:296-300
  • Codex no longer has file undo. Ghost-commit snapshots were turned on by default in Nov 2025 (openai/codex#6041) and got a v2 in Dec 2025 (openai/codex#8055). Current config code keeps the setting only for compatibility, "even though snapshots are no longer produced". thread/revert rewrites history only. codex-rs/core/src/config/mod.rs:231; app-server-protocol/src/protocol/v2/thread.rs:1288
  • Pi now has built-in MCP and optional extra tools. The Nov 2025 post predates this. MCP (pi mcp add), project trust, and optional grep/find/ls tools now ship in the box. The default tool set is still read/bash/edit/write, and plan mode and subagents are still left out on purpose. packages/coding-agent/docs/mcp.md; src/core/agent-session.ts:3652; README.md:19
  • Cline's docs and code disagree about checkpoints. The docs describe a shadow repo committed after every tool call. The current SDK snapshots once per user run (beforeRun) using git stash create plus a synthetic commit for untracked files. It keeps these alive under refs/cline/checkpoints/<session>/ inside the user's repo, with a scratch index file kept in Cline's data dir. docs/core-workflows/checkpoints.mdx vs sdk/packages/core/src/hooks/checkpoint-hooks.ts:21-437, 652

Not re-read from source this pass: Aider, OpenHands, Goose and DeepSeek Harness. Goose has moved to aaif-goose/goose. DeepSeek Harness exists (created 2026-08-13) as described. Treat those first-pass notes as unverified.

Harness today

The coding agent shares the general chat loop, so every finding below applies to all of chat, not only to coding.

  • Gap Tool history is dropped between turns. assemble_context rebuilds history from each message's text and sets tool_calls: None. ToolCallRecord stores only a tool name and the result payload, with no arguments or call ID. So on the next user message, the model has forgotten every file it read and every edit it made, unless it wrote them out in prose. src-tauri/src/chat/turn.rs:316-342; src-tauri/src/memory.rs:82

Steering in depth

Steering means adding an instruction to the running turn. Queueing means holding the message until the turn ends. Every implementation I checked applies a steer at a boundary: a tool call that has already started always finishes.

SourceWhere the steer landsDefault keyUnused steer at turn end
Pi (source)After the current assistant message's tool calls finish, before the next model call. Also re-checked after a long preparation step such as compaction.Enter steers, ⌥ Enter queues a follow-upThe loop keeps going while steers are pending
Codex (source)Through turn/steer into the active turn's pending input; rejected with ActiveTurnNotSteerable during review or manual compactionEnter steers, Tab queues (#9077)Server-side queue, thread/queue/*
Copilot SDK (docs)"Injected before the next LLM request"; a tool call already under way finishes firstThe SDK default is queue (enqueue); in Copilot CLI every prompt steersFalls back to the queue (the docs disagree on front or back)
OpenAI Responses (docs)Server-side response.steer over a WebSocket; the current output item and any hosted tools finish, then the response ends incomplete with reason steered and continues automaticallyn/aLives only on the open connection; lost if it drops

OpenAI's guide says server-side steering needs a newer model family over a WebSocket connection to the Responses API. Harness uses Chat Completions with gpt-5.4, so it can't use it today. That's acceptable: doing it in Harness's own loop matches Pi and works with any model. A Responses adapter can add server-side steering later as a speed-up, without changing the UI.

Proposed rules

  • Defaults. While a turn runs, Enter steers and ⌥ Enter queues a follow-up. Stop remains a separate button that cancels the turn. When the agent is idle, Enter starts a turn as it does now.
  • Boundary. A running tool call always finishes. Calls not yet started in the same batch get a {"skipped":true,"reason":"user sent a new instruction"} result, so the model reacts on its next call instead of after the whole batch. This is a deliberate step past Pi, which runs the full batch first.
  • Mid-text. If the model is only streaming text (no tool call in progress), abort that request, keep the partial text as the assistant message, add the steer, and send again. This matches what OpenAI's server does when it ends a response as steered.
  • During an approval. If a tool is waiting on its approval card, a steer counts as Deny with note for that call, with the steer text passed to the model. Copilot CLI documents this use.
  • Persistence. A steer is written to the transcript as a user message at the point it was applied, marked origin: "steer". Steers not yet applied are stored in the gated checkpoint, so they survive a restart the way pending approvals do now.
  • Turn ends first. If the turn finishes before a steer is applied, the steer becomes the next turn's opening message (the Copilot SDK fallback). Queued follow-ups go after it, one turn each.
  • UI. Pending steers and follow-ups show as chips above the composer, each with Edit, "Send as follow-up" and Remove. ⌥ ↑ pulls them back into the composer, as in Pi.

Undo in depth

Three designs have been shipped. Codex's history makes the main risk clear: snapshotting large untracked trees is slow and noisy. Codex spent several PRs on size limits and warnings, then stopped producing snapshots.

DesignBenefitsCosts
Separate git dir per project (OpenCode)Never touches the user's repo; works on folders that aren't git repos; a write-tree hash per step costs littleA second object store per project; needs gc and size limits; has to respect .gitignore
Stash-shaped commits under private refs in the user's repo (Cline SDK)Reuses the repo's object store; restores work with git stash applyWrites refs into the user's .git; needs a git repo; per run only
Ghost commits (Codex, removed)SimpleWarnings and slowness on large untracked files; removed

Recommendation: the OpenCode storage model with Cline's restore choices.

  • Store. <app data>/coding-snapshots/<hash(root)>/, used as git --git-dir=… --work-tree=<root>. Honor .gitignore plus the scope deny globs. Skip any single file over 2 MB and any untracked directory over a file-count limit, and record what was skipped in the snapshot so the UI can say "not covered".
  • When. One snapshot at turn start (the restore point the user sees) and one after each successful edit/write/mutating bash (so per-call diffs work). Each is a write-tree hash stored on the turn record. No commits.
  • Restore. On any user message: Restore files, Restore conversation, or Restore both. Files use read-tree + checkout-index -a -f, then delete files added since that snapshot. Take a snapshot just before restoring, so a restore can itself be undone once (OpenCode's unrevert).
  • Scope. Undo covers files in the scope only. It can't undo side effects of bash outside it (network calls, global installs, git push). The restore dialog should say so in one line.
  • What it unlocks. With undo in place, edits can run without asking by default (a setting, on by default), the way Cline's docs describe. The approval card then mostly appears for shell commands.

Tool display and UX

Steering and undo only work if you can see what the agent is doing. Today you mostly can't.

What a turn looks like today

  • Gap One card above the whole reply. Every tool call in a turn goes into a single ToolCallsCard placed above the assistant text. Text from all rounds is joined into one bubble underneath, so you can't tell what the agent said before or after a given action. src/renderer/chat/ChatMessageList.tsx:263-292; src-tauri/src/openai.rs:796
  • Gap Fixed labels, no detail. Completed rows show only "Read file", "Run command" or "Edit file". There's no path, command, exit code, output, duration or diff after an edit applies. The path and a preview clipped to 24 lines appear only while a call waits for approval. ToolCallsCard.tsx:15, 228-262; chatHelpers.tsx:450-496
  • Gap Errors look like success. toolIcon() always returns a checkmark, so a failed edit, a non-zero exit, a denied call and a successful call all look the same. chatHelpers.tsx:498-500
  • Gap No running state. Rust emits chat-tool-panel-update only after a tool finishes (or when it needs approval). During a two-minute npm test you only see the "THINKING" ticker. Command output is collected with wait_with_output and returned all at once. src-tauri/src/chat/tool.rs:186-196; coding/shell.rs:96-101
  • Gap Collapses at 2 calls. With two or more calls, the card collapses to a summary like "Read file (3), Run command". A 30-call coding turn becomes one line. chatHelpers.tsx:429-448
  • Gap Fragile matching. Updates are matched to rows by tool name and pendingId, and rows are keyed by array index. Two concurrent bash calls, or a reload in mid-turn, can attach a result to the wrong row. src/renderer/chat/ChatView.tsx:300-345
  • Gap Detail lost on reload. The saved ToolCallRecord has no arguments, so even with better rendering, an old turn couldn't show which command ran. src-tauri/src/memory.rs:82-87

How the reference harnesses do it

  • Codex: each action is an item with a lifecycle (item/started, deltas such as item/commandExecution/outputDelta and item/fileChange/patchUpdated, then item/completed), plus turn/diff/updated for the turn's combined diff and thread/tokenUsage/updated. app-server-protocol/src/protocol/common.rs
  • OpenCode: tool parts go pending → running → completed | error with start and end times. The shell tool streams its output into the part's metadata as it runs, keeping the last 30,000 characters. session/processor.ts:174-344; tool/shell.ts:27, 475-525
  • Pi: tool_execution_start / update / end events with partialResult, isError and durationMs; tool output is collapsed by default and Ctrl O expands it. coding-agent/docs/json.md:105-107; docs/keybindings.md

Proposed: a turn timeline

  • One item per action. Text segments, tool calls, steers, approvals, guard pauses and checkpoint markers render in order inside the assistant message. This replaces "card on top, joined text below".
  • Visible states. Preparing (arguments still streaming), Awaiting approval, Running (elapsed time, last lines of output), Done, Failed (exit code, first lines of stderr), Denied (with your note), Skipped (steered), Stopped. Each state has its own icon and color, not just a label.
  • A renderer for each tool.
    • read: path and line range; content hidden unless opened.
    • edit/write: path, +n −m, collapsed diff, Undo; on failure, the closest matching lines.
    • bash: the command as the title, live output tail, exit chip, duration; expanding shows full output with a note when truncated; a per-command Stop that kills only that process.
    • web_search/web_fetch: see Web search.
  • Grouping. Consecutive read-only calls (reads, rg, git status, searches) collapse into one "Explored 4 files" line. Edits, failures, approvals and long-running commands are never collapsed. This replaces "collapse at 2".
  • Turn status line. While a turn runs, a line pinned above the composer shows the current activity, the step count and elapsed time, the queue chips, and Stop. It replaces the ticker for coding turns and has an aria-live="polite" region.
  • Turn footer. When a turn ends: "Changed 3 files +40 −12 · 18 steps · 2m 10s" with Review changes (the turn's combined diff) and Restore…. If the turn hit the step cap or a guard, the footer says why.
  • Approvals stay in view. An approval waiting off-screen gets a pinned copy above the composer. If the window isn't focused, a system notification and Dock badge say the agent is blocked. Keyboard: ⌘ ↵ runs, Esc denies; Enter stays "steer".
  • Scrolling. Auto-follow while you're at the bottom, a "Jump to latest" pill otherwise. Live output scrolls inside its own box and never pushes the page.
  • Same view after reload. The timeline is rebuilt from the transcript sidecar, so an old turn looks the same as a live one.

What the backend has to provide

  • A stable itemId (the model's tool-call ID) on every event, replacing name-and-pendingId matching.
  • Events: chat-item-started, chat-item-delta (text or output chunks, throttled to about 10 per second, tail-capped), chat-item-completed (status, exit code, duration, diff stats), chat-turn-diff-updated. chat-stream-chunk and chat-tool-panel-update stay until the renderer has fully moved over.
  • bash streams stdout and stderr through piped readers instead of wait_with_output, with a kill handle per item.
  • The tool name is announced as soon as it appears in the SSE deltas, so a large write shows "Preparing write…" instead of a silent pause.
  • Diff stats computed in Rust after each edit, and stored with the item.

Web search

You use web search heavily in Claude, so treat it as a core tool. Harness has a basic one today.

Today

  • Gap A thin Tavily wrapper. search_depth: "basic", up to 10 results, snippets cut at 4,000 characters, include_answer: false, 45 s timeout, no retries. No domain filter, no recency filter, no news mode. It needs a separate Tavily key. src-tauri/src/chat/assistant_tools.rs:195-298; resources/contracts/tools.json:222-238
  • Gap Can't read a page. There's no fetch tool, so the model works from snippets and can't follow a link to the docs page or changelog it found.
  • Gap Searches run one at a time. The loop runs tool calls in sequence, so four queries cost four round trips. openai.rs:823-842
  • Gap Sources aren't shown. The card says "Web search" with no query, result list or links. Citations depend on the model choosing to include them.

Reference

  • OpenCode: websearch through Exa or Parallel (numResults, livecrawl, type: auto | fast | deep) and webfetch (URL to markdown, text or HTML; 5 MB cap; timeout up to 120 s). tool/websearch.ts:12-41; tool/webfetch.ts:9-50
  • Codex: the OpenAI-hosted web_search tool, with cached, indexed or live modes, domain filters, user location and context size. core/src/tools/hosted_spec.rs:14-44
  • Pi: none built in; available as an extension or MCP server.

Proposed

  • web_search v2: query, max_results, allowed_domains, blocked_domains, time_range (day, week, month, year), topic (general or news), depth (basic or advanced). It maps directly to Tavily's existing parameters, so the backend stays the same. Returns title, URL, published date and content for each result.
  • web_fetch (new): url, optional prompt, optional offset.
    • Fetches with reqwest and converts HTML to markdown. Caps size, caches for 15 minutes, upgrades http to https, and follows redirects only on the same host.
    • Blocks localhost, private IP ranges and file: URLs.
    • With a prompt, the page is answered by a small model (the existing gpt-5.4-mini setting) and only the answer reaches the main context. Without one, pages of markdown come back with an offset to read further.
  • Run read-only tools in parallel. When the model returns several read-only calls in one round (searches, fetches, reads), run them concurrently. Mutating tools stay in order. Pi does the same, running in parallel unless a tool is marked sequential. packages/agent/src/agent-loop.ts:517-519
  • Reliability. Retry 429 and 5xx with backoff; keep a clear error when no key is set; fall back from advanced to basic on timeout.
  • Display. The search card shows the query and a list of results (title, domain, date) you can open. The fetch card shows the URL, page title and size. The message ends with a Sources row built from every URL the turn searched or fetched, so citations don't depend on the model.
  • Safety. Page content is untrusted. The system prompt says so, and a fetched page never changes permissions. Web tools are read-only, so they run without approval.
  • Provider path. Put the provider behind a small trait. Tavily now; OpenAI-hosted search once the Responses adapter exists (no extra key, built-in citations); Exa as an option. This fits "wait for the model to get better": hosted search improves along with the model.

Both tools are available in ordinary chat as well as coding chats, and the iOS contract keeps its current web_search fields until iOS adopts the new ones.

Proposed composer

  • @ mentions. Typing @ opens a fuzzy file picker over the workspace (respecting .gitignore), like Codex's fuzzyFileSearch methods. The file shows as a chip with its relative path. At send time the content goes in as <file path="src/api.ts">…</file> (capped; larger files go in as a path with a note to read it) and is recorded as a read item, so the timeline and undo know about it.
  • Drops depend on what and where.
    • A file inside the workspace becomes an @ chip, not a copy.
    • A text file outside the workspace is still attached as content, as today.
    • A folder offers Use as project folder or Add to workspace (read-only or read-write).
    • An image becomes an image attachment.
  • Images. Paste, drop or pick PNG, JPEG, WebP or GIF. Stored with the same MessageAttachment record iOS uses, so they sync both ways. Sent as image content parts. Messages change from a string to a list of content parts. Steers can carry images too, as in Pi.
  • PDFs. Text extraction later; until then the rejection message names the formats that work.

Folder access today

  • One root per conversation (a project folder or Harness's own UI files). File tools resolve paths under that root, reject .. and symlinks that leave it, and skip the deny globs. Anything outside the root fails with "Invalid path". coding/scope.rs:161-253
  • run_command runs sh -lc in the root with no path checks. Once a command is approved it can touch anything your user account can.
  • The app isn't sandboxed (entitlements.plist has no app-sandbox key), so no security-scoped bookmarks are needed. macOS still asks once per protected location the first time Harness touches it: Desktop, Documents, Downloads, iCloud Drive, removable volumes. A refusal currently surfaces as a raw permission error.

Consistent rendering

  • resources/contracts/toolDisplay.json (new): for each tool, its label, past-tense label, icon key, which argument becomes the title (command, path, query, url), whether it counts as read-only for grouping, plus the state list and the grouping rule. Queueing work for the desktop

  • Projects list: the desktop syncs coding_projects.json ({id, name, kind}, no local paths) so the phone can pick a project.
  • Job: "Run on desktop" adds the user message to a conversation with desktopRun: {projectId, status: "queued", requestedAt} on the conversation. It syncs through R2 like any other change.
  • Pickup: when the desktop syncs and finds queued jobs, it shows a "2 tasks from iPhone" badge with Run / Dismiss for each. The run happens in that conversation with that project's scope. Status changes (running, waiting for approval, done, failed) and display items sync back.
  • Unattended runs: edits are auto-approved with undo; shell commands still follow the permission rules, so a job may pause for approval. The phone shows "Waiting for approval on desktop" instead of a spinner.
  • Safety: anyone who can write to the R2 bucket could queue a job, which means running code on the desktop. Default to asking before starting. Auto-start is a setting that's off by default, and even with it on, shell permissions still apply.

Target architecture

The loop moves out of openai.rs into a session object that owns the queues, the guard and the snapshots. openai.rs shrinks to a model adapter that streams one response. Ordinary chat uses the same loop, so steering works in chat too.

Why this shape keeps model upgrades simple

  • The model choice lives in one setting. The tools are generic (files and a shell), so a stronger model gets better without harness changes.
  • No model-specific prompt workarounds. Edit failure rate is the one number to track; if GPT models struggle with edits[], switching that model to apply_patch is a one-line change in the tool registry, as OpenCode does.
  • Moving to the Responses API later (for reasoning items and server-side steering) only touches the model adapter. The loop, queues, UI and contracts stay the same.

Phased plan

Ordered by value: steering, web search and undo are the three priorities, with the timeline in front because steering and undo need it. Each phase can ship on its own and stays within the Rust loop, one contract and one renderer surface where possible.

Phase 0 Replay tool history; replace the silent cap

  • Add the transcript sidecar; record full assistant tool calls (with IDs and arguments) and results for coding conversations.
  • assemble_context replays them, truncating results older than the last N turns to a stub.
  • Move the loop into chat/agent_loop.rs; the cap comes from agentLimits.json (desktop around 100); reaching it runs one text-only summary turn and emits chat-turn-completed{reason:"cap"}.

Acceptance

  • After a turn that read package.json, asking "what's the test script?" is answered without another read.
  • A task that needs 15 tool rounds completes; a task stuck at the cap ends with a visible summary and a "Step limit reached" note.
  • Restarting while an approval is pending still resumes (existing behavior); npm test passes.

Phase 1 Turn timeline and live tool status

  • Item events with stable IDs; bash output streaming with a per-command kill; tool name announced as soon as it streams in.
  • The assistant message renders as a timeline of items; renderers for read, edit, write, bash and web search; state icons; grouping of read-only calls; turn status line; turn footer with diff stats.

Acceptance

  • During pnpm test, the row shows the command, a running timer and the last lines of output within a second of each line printing.
  • A failed edit and a non-zero exit show a failure icon and the error; a success shows a checkmark.
  • Text the model wrote between two tool calls appears between them, not merged at the bottom.
  • Reloading the conversation shows the same timeline, including commands and exit codes.

Phase 2 Steering and the follow-up queue

  • Steer and follow-up queues in the AgentSession; chat:steer, chat:queueFollowUp, the queue events.
  • Composer: stays enabled while a turn runs; Enter steers, ⌥ Enter queues; queue chips with edit/remove; ⌥ ↑ pulls queued text back.
  • Skip-on-steer for calls not yet started; abort and resend when only text is streaming; a steer during a pending approval counts as deny with note.

Acceptance

  • While npm test runs, steering "use pnpm" results in the next model request containing that text; the running command is not killed; later calls in the same batch show "skipped".
  • A follow-up sent mid-turn starts its own turn after the current one finishes; the transcript shows both in order.
  • Quitting with a pending steer and relaunching keeps the steer in the queue.
  • Ordinary (non-coding) chat steers the same way.

Phase 3 Web search v2 and web fetch

  • Add filters, depth, topic and retries to web_search; add a new web_fetch (markdown, an offset for paging, an optional prompt answered by the mini model, SSRF guard, 15-minute cache).
  • Read-only calls in a round run in parallel; search and fetch cards; a Sources row on each message.
  • Doesn't depend on the coding work, so it can ship at any point.

Acceptance

  • "What changed in the latest Tauri release?" searches with time_range, fetches the release notes page, and answers with links; the Sources row lists every URL used.
  • Three searches in one round finish in about the time of the slowest one, not the sum.
  • web_fetch on http://localhost:5173 or http://10.0.0.1 is refused with a clear error.

Phase 4 Undo

  • coding/snapshot.rs with size limits; a snapshot at turn start and after each mutating tool.
  • A restore menu on each user message with Files / Conversation / Both; undo of a restore; per-change Undo on edit cards.

Acceptance

  • In a project folder that isn't a git repo, Restore files after a three-edit turn returns all three files byte-identical and removes a file the turn created.
  • The user's .git directory is unchanged (git status, refs and stash are identical before and after).
  • A repo with a 500 MB untracked folder still snapshots in under 1 s after the first run, and the menu lists the folder as not covered.

Phase 5 iOS view and run-on-desktop queue

  • toolDisplay.json plus a parity test (TS and Swift); synced items on assistant messages; the iOS timeline view. The contract can land earlier, during Phase 1.
  • coding_projects.json; "Run on desktop" on iOS; the desktop pickup badge with Run / Dismiss; job status synced back.

Acceptance

  • A coding turn run on the desktop shows on the phone with the same labels, states, commands and diff stats after a sync.
  • A job queued from the phone appears on the desktop after its next sync, waits for Run, and its result and status show on the phone after the following sync.
  • With auto-start off, nothing runs without a click on the desktop.
  • The label parity test fails if a tool is added to the contract but not handled on either platform.

Phase 6 Composer attachments

  • Messages become lists of content parts; image attachments (paste, drop, pick) using the existing MessageAttachment.
  • @ fuzzy file picker (coding:searchFiles); workspace files dropped or mentioned become path chips that are read at send time.
  • Folder drops offer "Use as project folder" or "Add to workspace".

Acceptance

  • Pasting a screenshot and asking "what's wrong with this layout?" sends the image, and the model describes it.
  • @api finds src/api.ts within 100 ms on a 10k-file repo; the sent message contains the file with its path, and the timeline shows a read item.
  • An image attached on desktop shows in the same conversation on iOS after a sync.

Phase 7 Four tools, AGENTS.md, permissions and workspace folders

  • codingTools.json becomes read, edit (edits[]), write, bash. AGENTS.md (or CLAUDE.md) from the scope root goes into the prompt.
  • codingPermissions.json plus coding/permissions.rs; the approval card offers once / always (conversation or project) / deny with note. Edits allowed by default now that undo exists (setting).
  • Workspace = root plus added folders (read-only or read-write) saved per project; outside reads ask with "Always allow this folder"; secret globs ask; best-effort path scan for bash; the workspace popover; a clear message on macOS refusals.

Acceptance

  • Approving npm test -- --run with "Always (project)" means npm test src/x runs without a card, in this conversation and in a new one.
  • npm test && rm -rf dist still asks, because the rm part isn't allowed.
  • Deny with note "use vitest directly" shows up in the model's next tool result; the turn continues.
  • No permission values remain hardcoded in Rust (grep AUTO_RUN_PREFIXES finds nothing).
  • Reading ~/Projects/other/README.md asks once; "Always allow this folder" lets later reads there through, also in a new conversation in the same project; a write there is refused.
  • Reading .env in the root asks.

Phase 8 Loop guard

  • chat/guard.rs; thresholds from the contract; a note added at 3, a pause card at 5 identical calls or 6 consecutive failures.

Acceptance

  • A scripted model that repeats the same failing edit pauses on the fifth attempt with a guard card. Continue resets the counter; typing a steer resumes with that text.

Phase 9 Compaction

  • Token usage from the stream; compact when context exceeds window minus 16k; keep the last 20k tokens plus all user messages word for word; the summary is a transcript entry, and the originals stay in the sidecar.

Acceptance

  • A long session crosses the threshold, compacts between rounds (not mid-tool), and the next steer still applies; the UI shows a "Context compacted" marker that expands to the summary.

Phase 10 Optional, each on its own

  • Responses API adapter, using server-side response.steer where the model supports it.
  • Seatbelt for bash (workspace write, network off, .git read-only), as Codex does.
  • A read-only preset (edits denied) offered as a toggle, if wanted.
  • Fork a conversation from any entry (the sidecar is already a tree).
  • A read-only explore subagent, only if compaction proves insufficient.
